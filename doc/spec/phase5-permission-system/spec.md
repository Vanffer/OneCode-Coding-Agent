# Permission System Spec

## 背景

Phase 3 让 OneCode 具备了多轮 ReAct Agent Loop：模型可以连续调用工具、读取结果、继续行动。Phase 4 又把系统提示升级为结构化 Prompt Runtime，让模型更稳定地遵守工具使用约定。

但当前工具执行仍然缺少真正的权限防线。模型一旦请求工具，系统主要依赖工具自身的语义和模式限制来约束行为。例如 Plan Mode 可以隐藏写类工具，但 Execute Mode 下 `bash`、`write_file`、`edit_file` 等工具仍然缺少统一的执行前权限判断。对于真实 coding agent 来说，这会带来几个风险：

- 危险命令可能在执行前没有被硬拦截。
- 文件读写可能越过项目目录边界。
- 不同用户、不同项目、不同本机环境无法声明差异化规则。
- 规则不明确时，系统无法把决定权交回用户。
- 工具被拒绝后，如果直接终止 Agent Loop，模型没有机会改用更安全的策略。

Phase 5 的目标是为 OneCode 引入一套分层权限系统：先用不可绕过的黑名单拦截高危操作，再用路径沙箱限制文件访问范围，再用可配置规则和权限模式做细粒度策略，最后由人在回路处理不明确的请求。权限拒绝应作为结构化工具结果回写给模型，让 Agent Loop 继续运行并尝试调整策略。

## 目标

- 在工具执行前增加统一权限判断，覆盖文件工具和命令工具。
- 对已知危险命令提供不可配置放开的硬拦截。
- 对文件读写搜索提供项目目录沙箱，防止路径逃逸。
- 支持用户级、项目级、本地级和会话级规则，并按优先级逐层判断。
- 支持用「工具名(模式)」声明 allow 或 deny 规则，覆盖命令、路径和参数模式。
- 支持多档权限模式，让用户能整体切换严格、默认、放行等信任等级。
- 在规则无法明确决策时触发人在回路确认，并支持本次、本会话、永久放行。
- 权限被拒绝时不终止 Agent Loop，而是把拒绝原因作为工具错误结果回写给模型。
- 保持 Phase 3/4 的 Agent Loop、Plan Mode、Prompt Runtime 和现有工具语义兼容。

## 功能需求

### F1: 统一执行前权限判断

系统应在任何工具真正执行前进行权限判断。

权限判断应覆盖：

- 命令执行工具。
- 文件读取工具。
- 文件写入工具。
- 文件编辑工具。
- 路径搜索和内容搜索工具。

如果权限允许，工具按原语义执行。
如果权限拒绝，工具本体不应被调用，系统应返回结构化工具错误结果。

### F2: 危险操作黑名单

系统应内置一组不可绕过的危险操作黑名单，用于在执行前拦截高危命令或明显危险参数。

黑名单规则应满足：

- 使用正则或等价模式匹配。
- 优先级高于所有用户配置、项目配置、本地配置、会话规则和权限模式。
- 不能被 allow 规则放开。
- 拒绝结果中应说明触发了危险操作拦截，但不需要暴露内部完整正则。
- 至少覆盖常见破坏性命令，例如递归删除根目录、格式化磁盘、强制清空系统目录等。

### F3: 路径沙箱

系统应限制文件相关工具只能访问项目目录内的路径。

路径沙箱应满足：

- 以当前项目目录作为默认沙箱根目录。
- 在权限判断前将目标路径转换为绝对路径。
- 在判断前解析符号链接。
- 解析后路径必须位于沙箱根目录内。
- 对不存在但即将创建的路径，应解析其已存在的最近父目录，再组合目标路径做边界判断。
- 不能通过 `..`、符号链接、绝对路径或路径大小写差异逃逸沙箱。
- 违反沙箱时应拒绝执行，并把错误作为工具结果回写给模型。

### F4: 路径沙箱覆盖范围

路径沙箱至少覆盖：

- 文件读取。
- 文件写入。
- 文件编辑。
- glob 搜索根目录。
- grep 搜索根目录和 glob 过滤结果。

对于命令执行工具，本阶段不做完整命令级文件路径解析，只由危险命令黑名单和规则引擎处理。

### F5: 可配置规则

系统应支持规则配置，用于声明某类工具调用允许或拒绝。

规则格式为：

```text
工具名(模式): allow
工具名(模式): deny
```

示例：

```text
Bash(git *): allow
Bash(rm -rf *): deny
ReadFile(src/**/*.go): allow
EditFile(src/internal/**): allow
WriteFile(**/*.env): deny
```

规则应支持：

- 工具名匹配。
- 精确模式匹配。
- glob 模式匹配。
- 对命令工具匹配命令字符串。
- 对文件工具匹配路径或搜索根目录。
- 对内容搜索工具匹配搜索根目录，也可匹配 glob 文件过滤模式。
- 规则结果只有 `allow` 或 `deny` 两种。

### F6: 规则配置层级

系统应从多个层级加载规则，并按优先级逐层判断。

优先级从高到低为：

```text
会话临时规则 > 本地级规则 > 项目级规则 > 用户级规则 > 权限模式默认策略
```

各层语义为：

- 用户级规则：用户机器上的全局默认规则。
- 项目级规则：项目仓库共享规则，适合提交到仓库。
- 本地级规则：项目目录中的本机私有规则，不适合提交到仓库。
- 会话临时规则：当前 TUI 进程内由用户确认产生的临时规则。

当高优先级规则命中时，低优先级规则不再参与判断。

### F7: 多档权限模式

系统应支持多档权限模式，用于控制规则未明确命中时的默认行为。

至少包括：

- Strict：规则未明确 allow 时默认询问或拒绝。
- Default：只读工具倾向允许，有副作用工具倾向询问。
- Permissive：低风险操作倾向允许，高风险操作仍需经过黑名单和沙箱。
- Bypass：尽量放行普通规则判断，但仍不能绕过危险黑名单和路径沙箱。

权限模式只作为最后的默认策略，不应覆盖黑名单、沙箱或明确 deny 规则。

### F8: 人在回路确认

当权限系统无法根据黑名单、沙箱、配置规则和权限模式直接给出明确 allow 或 deny 时，应触发用户确认。

确认信息应包含：

- 工具名。
- 参数摘要。
- 请求原因或风险摘要。
- 本次将要执行的具体命令或路径。
- 可选操作：拒绝、仅本次允许、本会话允许、永久允许。

用户选择后：

- 拒绝：本次工具不执行，返回权限拒绝工具结果。
- 仅本次允许：只允许当前这一次工具调用。
- 本会话允许：写入会话临时规则，当前进程后续相同模式自动允许。
- 永久允许：写入合适的持久化规则文件。

### F9: 永久允许写入位置

用户选择永久允许时，系统应写入本地级规则文件，而不是直接写入项目级共享规则。

这样可以避免用户在交互中意外修改团队共享策略。

项目级规则文件可以被手动编辑，但本阶段不通过确认交互自动写入项目级规则。

### F10: 权限拒绝不终止 Agent Loop

当某次工具调用被权限系统拒绝时，本次工具应返回 `IsError=true` 的结构化结果，并说明拒绝原因。

Agent Loop 不应因为单个权限拒绝直接终止。模型应能看到拒绝结果，并有机会：

- 换用更安全的工具。
- 缩小路径范围。
- 改用只读操作。
- 向用户解释无法继续的原因。

如果模型连续触发无效或被拒绝工具调用达到现有坏工具上限，Agent Loop 可以按保护机制停止。

### F11: TUI 权限交互

TUI 应能展示权限确认请求，并让用户选择拒绝、仅本次允许、本会话允许或永久允许。

在等待用户确认时：

- 当前 Agent Loop 暂停等待，不继续执行该工具。
- UI 不应冻结。
- 用户作出选择后，Agent Loop 继续。
- ESC 或取消当前任务时，等待中的确认应被取消，本次工具返回取消或拒绝结果。

### F12: 与 Plan Mode 兼容

Plan Mode 下仍然只开放只读工具。

即使权限规则允许写类工具，Plan Mode 也不能执行写文件、编辑文件或命令执行工具。

权限系统不应削弱现有 Plan Mode 的工具可见范围和禁用工具处理。

### F13: 与工具调度兼容

权限系统应与现有工具调度策略兼容：

- 只读工具仍可并发执行。
- 有副作用工具仍串行执行。
- 需要用户确认的工具调用应暂停在确认点。
- 并发只读批次中，如果某个工具需要确认，不应导致 UI 状态混乱。
- 权限判断结果应保持和原 tool call 一一对应。

### F14: 规则加载失败处理

如果某个规则配置文件不存在，应视为该层没有规则。

如果规则配置文件存在但格式错误，系统应给出清晰错误。

启动时加载配置失败时，应阻止进入不安全的运行状态，而不是静默忽略错误配置。

### F15: 权限决策可测试

权限系统的核心决策应能通过自动化测试覆盖。

测试应覆盖：

- 黑名单优先级。
- 沙箱路径逃逸。
- 符号链接逃逸。
- 不存在文件创建路径。
- 规则层级优先级。
- 权限模式默认策略。
- 用户确认结果转成临时或持久规则。
- 权限拒绝作为工具错误结果回写。

## 非功能需求

### N1: 安全优先

权限系统应默认保守。对于无法判断安全性的操作，应倾向于询问或拒绝，而不是默认放行。

危险黑名单和路径沙箱属于硬安全边界，不能被配置规则或权限模式绕过。

### N2: 向后兼容

现有六个核心工具的参数、返回格式和正常执行语义应保持兼容。

权限允许的情况下，工具行为应与 Phase 4 保持一致。权限拒绝只改变执行前的拦截行为。

### N3: Agent Loop 可恢复

权限拒绝应作为模型可观察的工具结果，不应直接变成系统崩溃、TUI 退出或 Agent Loop 终止。

模型应能基于拒绝原因调整后续策略。

### N4: UI 响应性

人在回路确认期间，TUI 应保持可响应状态。

用户应能取消当前任务，取消后 Agent Loop 不应继续等待旧确认或执行已取消的工具。

### N5: 可解释性

每个权限拒绝或确认请求都应有可读原因。

原因应帮助用户理解风险，也帮助模型调整策略，但不需要暴露全部内部规则实现细节。

### N6: 配置可维护

规则配置格式应简单、可读、可手写。

加载顺序和优先级应明确，避免用户不知道是哪一层规则生效。

### N7: 跨平台路径处理

路径沙箱应兼容 Windows 与类 Unix 系统。

路径比较应考虑当前平台的大小写、路径分隔符、卷名或根路径差异，避免 Windows 下通过大小写或盘符变化逃逸。

### N8: 测试不依赖真实 LLM

权限决策、规则匹配、沙箱判断、用户确认分支和 Agent 集成都应能通过 mock provider、fake tool 或本地临时目录测试。

核心安全行为不应依赖真实远程模型才能验证。

### N9: 最小权限系统范围

本阶段只实现工具执行前权限，不做更广泛的系统安全隔离。

权限系统应明确自己的边界，不声称能防住所有 shell 命令中的间接副作用。

### N10: 配置文件安全

自动写入永久允许规则时，应写入本地级规则文件。

写入前应保证目标路径位于预期配置目录内，避免通过路径配置造成写入逃逸。

## 不做的事

- **网络请求限制、资源配额、速率限制**：本阶段不限制出网，不做 CPU、内存、磁盘、速率或复杂运行时间配额。这些留给后续章节。
- **审计日志**：不落地权限决策的持久化审计流水，不提供安全审计查询能力。这些留给后续章节。
- **黑名单可配置或可扩展**：危险操作黑名单内置固定，用户不可增删、不可关闭，也不能通过 allow 规则绕过。
- **自动泛化规则**：人在回路选择“永久允许”时，只生成精确匹配规则。想要 `git *`、`src/**/*.go` 这类前缀或通配规则，需要用户手写配置文件。
- **非内置工具或 MCP 工具权限**：本阶段只覆盖 6 个内置工具，不处理未来 MCP 工具、插件工具或外部工具协议。
- **Bash 路径沙箱**：Bash 命令不做路径围栏，因为无法可靠静态解析任意 shell 命令的文件访问。Bash 风险由危险黑名单、规则引擎、权限模式和人在回路共同兜底。
- **多项目根或额外目录授权**：路径沙箱只认启动时的单一项目根，不支持运行时追加可访问目录，也不支持多 workspace root。
- **权限规则图形化或交互式编辑器**：规则依靠 YAML 配置文件和人在回路写入，不做专门的规则编辑 UI。
- **权限模式自定义档位**：模式集固定为 Strict、Default、Permissive、Bypass 四档，不做“仅自动批准某个工具”这类自定义自动批准档。
- **深层符号链接遍历围栏**：按模式找文件和搜内容的目录遍历沿用现有“不跟随目录符号链接”的行为；沙箱只校验搜索根和工具显式目标路径。
- **复杂 shell 语义解析**：不解析所有 shell 命令中的文件路径，不保证识别脚本内部、别名、函数、子进程或解释器内部产生的间接副作用。
- **复杂条件规则**：不实现按时间、用户身份、provider、模型、会话上下文或组合条件判断的规则表达式。
- **团队级规则同步或远程策略下发**：不做远程配置、组织策略、团队同步或集中管控。
- **自动写入项目级共享规则**：人在回路不会自动修改项目级规则文件；永久允许只写入本地级规则文件。
- **改变工具 schema 或成功结果格式**：不改变现有 6 个核心工具的参数 schema 和成功结果格式。
- **替代 Plan Mode 工具可见范围限制**：Plan Mode 仍然由 Agent 模式控制，只开放只读工具；权限系统不能让 Plan Mode 执行写类或命令类工具。

| ID | 对应需求 | 验收标准 | 验证方式 |
|----|---------|---------|---------|
| AC1 | F1 | 所有 6 个内置工具在执行前都会经过统一权限判断 | 使用 fake tool 或 spy registry 断言权限拒绝时工具本体未被调用 |
| AC2 | F2 | 危险黑名单能拦截内置高危 Bash 命令，并且 allow 规则、权限模式、会话规则都不能放行 | 用多组高危命令测试黑名单优先级 |
| AC3 | F3/F4 | 文件读取、写入、编辑、glob 根目录、grep 根目录无法通过 `..`、绝对路径或符号链接逃逸项目根 | 使用临时目录和符号链接测试沙箱 |

| AC12 | F12 | Plan Mode 下即使规则允许写类工具，也不能执行写文件、编辑文件或 Bash | 在 Plan Mode 构造允许规则并请求写工具，断言仍被模式禁用 |
| AC13 | F13 | 只读工具仍可并发；有副作用工具仍串行；权限判断不会破坏 tool result 与 tool call 的对应关系 | 使用 scheduler 测试验证顺序和结果对应 |
