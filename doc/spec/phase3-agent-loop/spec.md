# Agent Loop Spec

## 背景

Phase 2 已经为 OneCode 引入了工具系统：模型可以看到工具定义，发起一次工具调用，本地执行工具后把结果回灌给模型，再由模型生成最终回复。

但当前闭环仍然是最小验证形态：一次用户请求最多执行一个工具调用，然后进入最终回复阶段。它无法独立完成需要多步探索、连续读写、搜索后再修改、修改后再测试这类真实编码任务；也无法在同一轮里处理多个工具调用、取消正在进行的任务、区分只读计划与实际执行。

本阶段要把 OneCode 从“单次工具调用助手”推进到“可自主多步执行任务的 Agent”。核心范式是 ReAct：模型根据当前上下文思考下一步，调用工具观察结果，再基于观察继续行动，直到任务完成或触发停止条件。

## 目标

- 支持完整的 ReAct agent loop：一轮轮请求模型、执行工具、回写结果、继续请求模型。
- 让工具结果真正成为后续模型决策的输入，支持多步任务自主推进。
- 提供统一异步事件流，让 Agent 编排和 TUI 渲染彻底解耦。
- 支持实时流式展示，同时保留完整响应用于循环判断和对话历史写入。
- 支持一次模型响应中的多个工具调用，并按安全性分批执行。
- 支持 Plan Mode 两段式工作流：`/plan` 只允许只读工具产出计划，`/do` 基于待执行计划开放全工具执行。
- 提供多种停止条件，避免无限循环、无效工具调用风暴或错误后失控。

## 功能需求

### F1: 多轮 ReAct 循环

Agent 接收一条用户任务后，应持续执行“请求模型 → 收集模型输出 → 执行工具 → 回灌工具结果 → 再请求模型”的循环。

当模型没有再请求工具，并输出可作为最终答复的文本时，本轮任务结束。

### F2: 工具结果回写到后续决策上下文

每次工具执行完成后，工具调用与工具结果都必须进入会话上下文。后续模型请求必须能看到前面工具的成功结果或错误结果，并据此继续行动、重试、换策略或总结给用户。

### F3: 多工具调用处理

如果模型在一次响应中返回多个工具调用，Agent 不应只取第一个。Agent 应收集本次响应中的全部工具调用，并为每个调用产生对应工具结果。

所有工具结果回写完成后，Agent 再发起下一轮模型请求。

### F4: 按安全性分批执行工具

同一批工具调用应根据工具安全属性分组执行：

- 只读、无副作用、彼此独立的工具可以并发执行。
- 可能改变文件、执行命令或产生外部副作用的工具必须串行执行。
- 当同一批工具调用同时包含只读工具和有副作用工具时，执行顺序必须可预测，避免并发修改导致结果不稳定。

本阶段只实现内置工具的固定安全分类，不做用户确认或动态权限判断。

### F5: 统一异步事件流

Agent 对外输出一套异步事件流，至少覆盖以下事件：

- 文本增量：模型流式输出的可见文本。
- 工具调用开始：工具名、参数摘要、调用标识。
- 工具调用结果：调用标识、结果摘要、是否错误。
- Token 用量：本轮或累计的输入、输出、总 token 信息；如果某个 provider 无法提供，应明确表现为不可用。
- 进度状态：当前处于请求模型、等待工具、执行工具、继续循环、完成、取消或错误等阶段。
- 完成事件：本次 agent loop 正常结束。
- 错误事件：流式请求、工具执行、协议解析等错误。

TUI 只消费事件并渲染，不直接理解 provider 协议或工具执行细节。

### F6: 流式收集器双路输出

每轮模型流式响应都要同时完成两件事：

- 实时把文本增量推送给界面，让用户看到模型正在输出。
- 在内部累积完整响应，包括文本、工具调用、结束原因和用量信息，用于写入会话历史与判断下一步动作。

流式响应中出现工具调用时，Agent 应能正确收集完整参数，而不破坏已有文本增量展示。

### F7: 停止条件

Agent loop 必须支持多种停止条件：

- 模型输出最终答复且没有继续请求工具。
- 达到 agent loop 迭代上限。
- 用户按 ESC 取消当前任务。
- 连续请求未知工具或当前模式禁用工具，达到限制后停止。
- LLM 流式请求出错。
- 工具执行出现不可继续的系统性错误。

迭代上限是兜底机制，应允许复杂任务有足够空间，不应过小导致正常多步任务频繁中断。

### F8: ESC 取消当前任务

当用户在任务执行中按 ESC 时，当前 agent loop 应尽快取消：

- 正在进行的模型流式请求应停止。
- 正在等待或尚未开始的工具调用不再继续。
- 正在执行的工具应接收到取消信号；如果工具无法立刻停止，Agent 至少应不再进入下一轮模型请求。
- UI 应显示任务已取消，并恢复到可继续输入的状态。

取消只影响当前任务，不清空已有会话历史。

### F9: 未知工具与禁用工具处理

当模型请求不存在的工具，或在当前模式下禁用的工具时，Agent 应把该情况作为结构化工具错误回写给模型，使模型有机会纠正。

如果模型连续多次请求未知工具或禁用工具，Agent 应停止本次 loop，并向用户说明停止原因。

### F10: Plan Mode 两段式

系统支持两个用户命令：

- `/plan`：进入计划阶段，只开放只读工具。模型可以读取文件、搜索代码、查看信息，但不能写文件、编辑文件或执行有副作用命令。计划生成后保存为待执行计划。
- `/do`：如果存在待执行计划，则进入执行阶段，开放全部工具，让模型基于这份计划完成任务。

执行阶段完成、取消或失败后，待执行计划应被清理或标记为已处理，避免下一次 `/do` 误执行旧计划。

### F11: Plan Mode 的用户体验

`/plan` 产出的计划应作为普通助手回复展示给用户，同时进入会话上下文。`/do` 启动时应让模型明确知道当前要执行的是最近一次待执行计划。

如果用户在没有待执行计划时输入 `/do`，系统应给出可读提示，而不是发起普通 agent loop。

### F12: 与现有工具系统兼容

现有六个核心工具继续可用。读文件、glob、grep 属于只读工具；写文件、编辑文件、bash 属于有副作用或潜在危险工具。

本阶段不改变工具本身的用户可见语义；重点是改变 Agent 如何多轮调度、回灌和停止。

### F13: 跨 Provider 行为一致

Anthropic 与 OpenAI 两种 provider 都应支持多轮工具调用、多个工具调用收集、工具结果回写、流式文本展示、错误事件和可用时的 token 用量事件。

协议差异应收敛在 provider 适配层或统一抽象层内，不泄漏到 TUI。

## 非功能需求

### N1: UI 响应性

Agent loop 执行期间，TUI 不应冻结。文本、工具事件、进度和取消都应通过异步事件驱动。

### N2: 状态可解释

用户应能从界面看出当前大致处于哪个阶段：模型正在输出、工具正在执行、继续下一轮、任务完成、任务取消或出错。

### N3: 循环安全

Agent loop 必须有明确上限和错误停止机制，不能因为模型持续请求工具而无限运行。

### N4: 工具执行确定性

对有副作用工具采用串行执行，避免并发写入、并发命令执行或读写交错造成不可预测结果。

### N5: 向后兼容

普通聊天、单次工具任务、现有六个工具的参数和返回格式应保持兼容。用户不使用 `/plan` 或 `/do` 时，仍可正常直接提出任务。

### N6: 可测试性

Agent loop 的循环、停止条件、工具分批、模式限制和事件流应能通过单元测试或集成测试验证。测试不应依赖真实远程 LLM 才能覆盖核心编排行为。

### N7: 上下文体量意识

本阶段不做上下文压缩，但 Agent 应避免额外制造无意义的大量消息。工具结果仍沿用现有工具自身的截断与限制策略。

## 不做的事

- **权限系统**：不做用户确认、不做 allow/deny 规则、不做命令审批。
- **上下文压缩**：不做自动摘要、历史裁剪或长期记忆。
- **用户交互式确认**：Agent loop 中途不暂停询问用户是否继续执行某个工具。
- **工具动态风险判定**：本阶段只按工具类别做固定安全分类，不解析命令内容判断危险程度。
- **MCP 或外部工具协议**：只调度现有内置工具。
- **持久化计划**：待执行计划只保存在当前进程会话内，退出后不恢复。
- **并发写操作**：有副作用工具不并发执行。
- **复杂任务队列**：同一时间只处理一个用户任务，不支持后台多任务并行。
- **成本统计或计费估算**：只展示 token 用量，不计算价格。

## 验收标准

| ID | 对应需求 | 验收标准 | 验证方式 |
|----|---------|---------|---------|
| AC1 | F1/F2 | 一个需要“搜索文件 → 读取文件 → 修改文件 → 运行测试”的任务能在同一次用户请求中连续执行多轮工具调用，并基于每次结果继续下一步 | 使用 mock provider 或真实 provider 跑端到端任务，观察工具结果逐轮进入后续决策 |
| AC2 | F3 | 模型一次返回多个工具调用时，Agent 会执行全部调用并回写对应结果，而不是只执行第一个 | 用 mock provider 返回两个只读工具调用，断言产生两个工具结果 |
| AC3 | F4/N4 | 多个只读工具可并发执行；有副作用工具串行执行；混合批次执行顺序稳定 | 用可控测试工具记录开始/结束顺序并断言 |
| AC4 | F5/N1 | TUI 通过统一事件流展示文本、工具开始、工具结果、进度、完成和错误，不直接调用 provider 或工具 | 跑一次多工具任务，观察 UI 事件渲染；检查调用边界 |
| AC5 | F6 | 流式文本能实时显示，同时完整响应被保存并用于判断是否继续调用工具 | 用 mock stream 分片输出文本和工具调用，断言 UI 收到增量且会话历史完整 |
| AC6 | F7/N3 | 当模型持续请求工具超过迭代上限时，Agent 停止本次任务并给出可读原因 | mock provider 连续返回工具调用，观察达到上限后停止 |
| AC7 | F8 | 执行中按 ESC 会取消当前任务，停止后续 LLM 请求和未开始工具，UI 回到可输入状态 | 在 TUI 中启动长任务后按 ESC，观察取消提示与状态恢复 |
| AC8 | F9 | 连续请求未知工具或禁用工具达到限制后，Agent 停止 loop，并向用户说明原因 | mock provider 连续请求不存在工具或 Plan Mode 禁用工具 |
| AC9 | F10/F11 | `/plan` 只开放只读工具，生成计划并保存为待执行计划；`/do` 基于该计划开放全部工具执行 | 在 TUI 输入 `/plan` 后尝试触发写工具应被禁用；再输入 `/do` 可执行写工具 |
| AC10 | F11 | 没有待执行计划时输入 `/do`，系统给出提示，不发起普通 agent loop | 清空待执行计划后输入 `/do`，观察提示 |
| AC11 | F12/N5 | 现有六个工具的参数和用户可见结果语义保持兼容，普通聊天和单次工具任务仍正常 | 运行 Phase2 工具相关测试和一次普通聊天 smoke test |
| AC12 | F13 | Anthropic 与 OpenAI provider 都能完成多轮工具调用和多工具调用收集；不支持 token 用量时以不可用状态表达 | 分别使用两个 provider 的 mock 或真实配置验证相同行为 |
| AC13 | N2 | 用户能从界面看到请求模型、执行工具、继续下一轮、完成、取消、错误等进度状态 | 跑成功、取消、错误三类场景并观察状态栏或输出区 |
| AC14 | N6 | Agent loop、停止条件、工具分批和模式限制都有不依赖真实 LLM 的自动化测试覆盖 | 运行测试命令，相关测试通过 |
| AC15 | 不做的事 | 本阶段没有引入权限确认、上下文压缩、持久化计划或外部工具协议 | 检查功能入口和文档，确认这些能力未出现 |
