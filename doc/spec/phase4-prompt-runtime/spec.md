# Structured System Prompt Runtime Spec

## 背景

Phase 3 已经让 OneCode 具备了基础 Agent 能力：它可以通过 ReAct loop 多轮请求模型、执行工具、回写工具结果，并支持 Plan Mode 与 Execute Mode 的两段式流程。

但当前系统提示仍然是一个全局静态文本。身份设定、行为准则、工具使用规则、Plan Mode 约束、Execute Mode 约束等内容都混在同一份 System Prompt 中。这会带来几个问题：

- 不同职责的指令耦合在一起，后续插入项目指令、Skill、记忆、权限规则时容易变得混乱。
- 稳定指令和动态信息没有区分，无法明确利用模型 API 的 prompt cache 能力。
- Plan Mode 等会话状态规则长期存在于全局提示中，可能影响普通执行模式。
- 环境信息、模式提醒、临时约束缺少统一注入机制，容易被模型当成普通用户输入处理。
- 工具使用关键规则只在系统提示中出现一次，模型在复杂多轮任务中可能忘记或弱化遵守。

Phase 4 的目标是把 OneCode 的系统提示从“单个全局文本”升级为“结构化 Prompt Runtime”：稳定模块按优先级装配，动态上下文按运行时注入，模式规则按轮次提醒，并能观测缓存命中情况。这样 OneCode 不只是能调用工具完成任务，而是能更稳定、更省 token、更符合 coding agent 行为预期地完成任务。

## 目标

- 将全局系统提示拆成职责明确、顺序稳定、可组合的模块。
- 区分稳定内容和动态内容，让稳定指令与工具描述具备进入缓存通道的条件。
- 支持通过系统级补充消息注入环境信息、运行模式提醒和临时系统约束。
- 让 Plan Mode 等会话级规则只在对应模式下按轮次注入，避免污染普通执行模式。
- 在系统提示和工具描述中双重强化关键工具规则，提高模型遵守率。
- 从模型 API 返回信息中提取缓存相关用量，帮助验证缓存策略是否实际生效。
- 准备一组典型人工对比场景，用于观察结构化提示改造前后的行为差异。

## 功能需求

### F1: 结构化系统提示模块

系统应将原来的全局系统提示拆分为多个固定模块，每个模块只表达一种职责。

固定模块至少包括：

- 身份设定
- 系统约束
- 任务模式
- 动作执行
- 工具使用
- 语气风格
- 文本输出

这些模块必须按明确优先级从前到后拼接。模块之间使用空行分隔，方便阅读、测试和后续扩展。

### F2: 可选提示模块

系统应预留可选模块位置，用于后续接入自定义指令、已激活 Skill、长期记忆等扩展内容。

本阶段只实现模块位置与装配能力，不实际加载项目指令文件、自动记忆或真实 Skill 内容。

### F3: 稳定内容与动态内容分离

系统应明确区分稳定提示内容和动态提示内容。

稳定内容包括长期不变的身份、行为准则、工具使用规则、输出风格等。动态内容包括工作目录、当前日期、运行模式、轮次提醒、会话历史等。

稳定内容应通过适合缓存的通道传给模型；动态内容应通过运行时消息或系统级补充消息传给模型，避免因为频繁变化破坏缓存效果。

### F4: 系统级补充消息

系统应支持一种特殊形式的系统级补充消息，用于在运行中注入环境信息、临时约束和模式提醒。

这类补充消息应具备以下行为：

- 不写入长期会话历史。
- 不被当作用户自然语言输入回复。
- 优先级高于普通用户消息。
- 可以用特殊标签包裹，例如 `<system-reminder>`。
- 能被 Provider 适配层转换为对应模型 API 支持的消息形式。

### F5: 环境信息运行时注入

系统应在每轮模型请求时注入必要环境信息，例如当前工作目录、操作系统、当前日期、当前运行模式等。

环境信息应作为动态系统级补充内容注入，不应拼进稳定系统提示主体。

本阶段只注入本地运行时可直接获得的环境信息，不加载项目规则文件。

### F6: Plan Mode 轮次提醒

Plan Mode 约束不应长期写入全局系统提示主体。

当 Agent Loop 处于 Plan Mode 时，系统应按轮次注入 Plan Mode reminder：

- 第 1 轮注入完整 Plan Mode 规则。
- 之后每隔固定轮次重新注入完整规则。
- 其他轮次可以注入精简提醒，或在满足上下文稳定性的前提下不注入。
- 提醒内容不写入会话历史。

这可以避免模型在多轮工具调用后忘记仍处于只读规划模式，同时避免 Plan Mode 规则影响 Execute Mode。

### F7: 关键工具规则双重强化

系统应在结构化系统提示和工具描述中同时强化关键工具使用规则。

至少包括：

- 涉及代码或文件时优先使用专用工具读取真实上下文。
- 编辑文件前必须先读取相关文件。
- 精确修改优先使用编辑工具。
- 搜索文件路径优先使用 glob。
- 搜索文件内容优先使用 grep。
- 工具失败时必须阅读错误并调整策略，而不是忽略错误。

工具描述应补充这些规则，使模型在选择工具时也能看到对应约束。

### F8: Provider 缓存映射

Provider 适配层应能区分稳定系统提示、工具定义和动态补充消息，并尽量映射到各模型 API 支持的缓存友好形式。

如果某个 Provider 暂不支持显式缓存控制，也应保持统一抽象，让上层逻辑不依赖具体 Provider 差异。

### F9: 缓存用量解析

系统应从模型 API 返回的 usage 或等价字段中提取缓存相关信息。

至少应能表达：

- 是否提供缓存信息。
- 缓存创建 token 数。
- 缓存命中读取 token 数。
- 普通输入 token 数。
- 输出 token 数。
- 总 token 数。

当某个 Provider 不提供缓存字段时，应明确标记为不可用，而不是伪造为 0。

### F10: Prompt 组装可测试

结构化系统提示的组装结果应可被测试验证。

测试应覆盖：

- 固定模块顺序稳定。
- 模块之间格式稳定。
- 动态环境不进入稳定提示主体。
- 可选模块位于固定模块之后。
- Plan Mode reminder 只在 Plan Mode 下按规则出现。
- Execute Mode 不包含 Plan Mode 完整约束。

### F11: 人工对比场景

系统应准备一组典型人工对比场景，用于观察改造前后的模型行为。

场景至少包括：

- 普通代码修改任务是否会先读文件再编辑。
- 搜索任务是否优先使用 glob 或 grep。
- Plan Mode 是否保持只读并输出计划。
- 多轮 Plan Mode 是否仍记得只读约束。
- 工具报错后是否会根据错误调整策略。
- Provider 返回 usage 时是否能看到缓存相关字段。

本阶段只准备场景说明和观察方法，不做自动化评估框架。

## 非功能需求

### N1: 向后兼容

普通聊天、普通执行模式、已有工具调用、Plan Mode 与 Execute Mode 的用户可见流程应保持兼容。

结构化系统提示改造不应改变用户输入命令的语义，也不应破坏 Phase 3 已经实现的 Agent loop、工具回写、取消和 pending plan 流程。

### N2: Provider 差异封装

不同模型 API 对 system prompt、缓存控制、工具定义和补充消息的支持方式不同。系统应将这些差异限制在 Provider 适配层或 Prompt Runtime 的映射层中。

Agent loop 和 TUI 不应直接依赖某个具体 Provider 的缓存字段或消息格式。

### N3: 缓存友好

稳定提示内容和工具定义应保持顺序稳定、文本稳定、格式稳定，避免因为无意义变化导致缓存失效。

动态内容应避免拼接进稳定提示主体。

### N4: 可观测性

系统应能通过事件、日志或测试输出观察 prompt 组装结果和缓存用量信息。

当缓存字段不可用时，应明确展示不可用状态，而不是让用户误以为缓存没有命中。

### N5: 可维护性

新增或调整提示模块时，应能在一个清晰的位置完成，不需要同时修改多个 Provider 的业务逻辑。

模块命名、职责、优先级和拼接规则应清楚，避免回到单个大 prompt 文本的状态。

### N6: 可测试性

Prompt 组装、动态 reminder 注入、缓存 usage 解析、Provider 消息映射应具备自动化测试覆盖。

核心行为应能用 mock 或本地构造数据验证，不依赖真实远程 LLM 才能测试。

### N7: 安全边界清晰

结构化提示应继续强调安全边界，例如不覆盖用户未授权的改动、不忽略工具错误、不在 Plan Mode 执行写操作。

本阶段不引入新的权限系统，但不能削弱 Phase 3 已有的模式限制和工具安全分类。

### N8: 控制上下文体量

运行时补充消息应控制长度和注入频率，避免每轮重复注入大段动态指令导致上下文膨胀。

Plan Mode reminder 应按首轮完整、间隔轮次重复的策略控制频率。

## 不做的事

- 不加载项目级指令文件，例如仓库内的自定义规则文件或用户本地规则文件。
- 不实现自动记忆、长期记忆写入或记忆检索。
- 不接入真实 MCP 服务，也不实现 MCP 工具描述注入。
- 不实现自动化评估框架；本阶段只准备人工对比场景。
- 不新增用户交互式权限确认流程。
- 不实现命令级风险审批或 bash 命令 allow/deny 规则。
- 不做上下文压缩、历史摘要或自动裁剪。
- 不持久化 Prompt Runtime 状态。
- 不改变现有六个核心工具的用户可见参数和返回语义。
- 不要求所有 Provider 都必须真实支持显式 prompt cache；不支持时只需要通过统一抽象表达不可用。

## 验收标准

| ID | 对应需求 | 验收标准 | 验证方式 |
|----|---------|---------|---------|
| AC1 | F1 | 系统提示被拆分为七个固定模块，并按身份、系统约束、任务模式、动作执行、工具使用、语气风格、文本输出的顺序稳定拼接 | 查看 prompt 组装测试，断言模块顺序和分隔格式 |
| AC2 | F2 | 可选模块能够追加到固定模块之后，且本阶段不实际加载项目指令、Skill 或长期记忆 | 使用测试构造可选模块，断言位置正确；检查没有新增加载入口 |
| AC3 | F3 | 稳定提示主体中不包含工作目录、日期、当前模式、轮次等动态信息 | 查看 prompt 组装测试与实际构造结果 |
| AC4 | F4/F5 | 每轮模型请求会收到系统级补充消息，包含必要环境信息，且该消息不写入会话历史 | 使用 mock provider 观察收到的消息；断言 conversation 历史不包含 reminder |
| AC5 | F6 | Plan Mode 第 1 轮注入完整 reminder，间隔轮次重复完整 reminder，Execute Mode 不注入完整 Plan Mode 约束 | 使用 Agent loop 或 prompt runtime 测试不同轮次和模式 |
| AC6 | F7 | 系统提示和工具描述都包含关键工具规则，例如编辑前先读、搜索路径用 glob、搜索内容用 grep、工具失败后调整策略 | 检查 prompt 构造结果和工具定义描述 |
| AC7 | F8/N2 | Provider 适配层可以接收稳定系统提示、动态补充消息和工具定义，Agent/TUI 不依赖具体 Provider 消息格式 | 查看接口边界和编译依赖；使用 mock provider 验证调用 |
| AC8 | F9 | usage 中能够表达缓存信息是否可用、缓存创建 token、缓存命中 token、输入 token、输出 token、总 token | 使用 provider usage 映射测试验证字段 |
| AC9 | F9 | Provider 不提供缓存字段时，缓存信息标记为不可用，不伪造为 0 命中或 0 创建 | 使用 mock usage 或 provider 单元测试验证 |
| AC10 | F10/N6 | Prompt 组装、动态 reminder、缓存 usage 解析都有自动化测试覆盖 | 运行测试命令，相关测试通过 |
| AC11 | F11 | 文档中包含人工对比场景，覆盖普通编辑、搜索、Plan Mode、多轮 reminder、工具错误和缓存 usage 观察 | 查看人工场景文档 |
| AC12 | N1/N7 | Phase 3 的普通执行、Plan Mode、工具调用、取消和 pending plan 流程仍然可用 | 运行已有 Agent/TUI 相关测试和一次启动 smoke |
| AC13 | N3/N8 | 稳定提示文本顺序稳定，动态提醒按频率注入，不会每轮重复完整大段 Plan Mode 规则 | 查看测试和 prompt 注入策略 |
| AC14 | 不做的事 | 本阶段没有新增项目指令加载、自动记忆、真实 MCP、权限确认、上下文压缩或工具语义变更 | 检查代码入口、文档和测试范围 |
